# Hand-off plans, written 2026-11-12

Six pieces of work that came out of a design and bug review of the whole
project and were too big, or too dependent on a measurement, to finish in that
session. Each is written to be picked up cold by a smaller model: it says what
is wrong, where the code is, what to build, how to test it, when it is done and
what **not** to do. They are independent; do them in any order. The order below
is by value to the owner's book.

What the same session already shipped (so do not rebuild it) is in
`../STATUS.md` under 2026-11-12: refreshing one spread inside an existing
document, an assemble that cannot destroy the old document by failing, pages
left out of a document being named, the editor refusing to overwrite a newer
document, and four smaller fixes.

House rules that apply to every item (from `../../CLAUDE.md`, restated because
they are the ones a newcomer breaks):

- Run tests at below-normal priority, with the exact wrapper in the global
  instructions. The full suite is `pipeline/tests server/tests tools/tests`.
- A number that judges a change is **pre-registered** first
  (`docs/data/<name>_prereg_<date>.md`: the population, the statistic, the
  gate), has a **control**, and goes into `docs/RESULTS.md` as a new dated row.
  A refusal is a result and is written down the same way.
- Never claim text got better from a confidence number; show a text diff.
- A model's or a rule's decision is a **flag the operator can undo**, never a
  deletion.
- Do not touch the thresholds listed under "Guardrails" in `CLAUDE.md`.

## 1. Carry hand edits across a spread refresh when the page did not move

**DONE 2026-11-12** (Stage 07 v0.3.0, `--carry-edits` / `?carry=true`; RESULTS
2026-11-12, carry row; pre-registration `../data/carry_edits_prereg_20261112.md`).
Two departures from the text below, both forced by the code: the carry runs
AFTER the unreadable-panel pass, not before `_merge_pages` (that pass rewrites
`type_auto` and clears pairs on the blocks it converts), and a hand-set reading
order is carried as one edit of the page, only when the blocks match one for one
(one drag renumbers the whole page).

**Problem.** `python -m pipeline.stage07_assemble <job> --spread page_NNN`
(and the console's "Update this spread in the document") rebuilds one spread.
If that spread carries hand edits it refuses, and `--force` discards them. That
is right when the page was re-cropped (a hand-drawn book box moves every word
box). It is needlessly destructive when the page was re-run and came out the
same — re-run after a crash, or to pick up a newer figure upgrade.

**Build.** In `pipeline/stage07_assemble.py`, after the fresh `DocPage`s for a
refreshed spread exist and before `_merge_pages`, add `_carry_edits(old_pages,
new_pages) -> dict` that copies edits from the old page to the new one **only
on an exact match**:

- Pages match by `page_id`, and only if `width`/`height` are equal. Otherwise
  carry nothing for that page.
- A word edit (`edited`, `text`) is carried when the new page has a word with
  the same block `bbox`, the same word `bbox` and the same `text_ocr`. Set
  `text` and `edited` on the new word; leave `text_ocr` alone.
- Block-level work (`text` override, `structure_edited` with its `type` and
  `reading_order`, `order_confirmed`, `deleted`, `pair_source == user` with its
  `figure_ref`, `is_surface` set by hand) is carried when the new page has a
  block with the same `bbox` **and** the same `type_auto` and `order_auto`.
  A `figure_ref` is carried only if the block it points to was itself matched.
- A merged picture (the editor's "merge with the picture below") changes a
  block's `bbox` and removes blocks, so it will not match. **Do not try to
  replay a merge.** Count it as not carried.
- Return `{"words_carried", "words_dropped", "blocks_carried",
  "blocks_dropped", "dropped": [...]}` and put it in the refresh record in
  `document.meta.json`.

Then change the guard: with edits present and no `--force`, still refuse — but
add a third mode, `carry=True` (`--carry-edits`, `?carry=true`), that refreshes
and carries, and **refuses if anything would be dropped** unless `--force` is
also given. The console button asks: "N edits can be kept, M cannot (list).
Continue?".

**Tests** (extend `pipeline/tests/test_stage07_refresh.py`): identical re-run
carries a word edit and a block text override; a re-run with a shifted word
box drops that word and reports it; a page whose size changed carries nothing;
`carry` without `force` refuses when something would be dropped and leaves the
document byte-identical; provenance (`text_ocr`, `type_auto`, `order_auto`) is
never changed.

**Check on real data.** Extend `tools/spread_refresh_check.py`: after the hand
edit, refresh the *edited* spread with `carry` and require the document to be
identical to the saved one (the trace did not change, so everything must
carry). That is the control.

**Do not** match by word text alone, by position "within a few pixels", or by
order in the list. A carried edit on the wrong word is a silent wrong
correction; a dropped edit is a visible loss the operator can redo.

**Done when:** the tests pass, the control passes on `jobs/tablegrid_e2e` and
`jobs/20261021-104424-6d43b587`, and a RESULTS row records both.

## 2. Show which stages of a page are left over from an earlier run

**DONE 2026-11-12** (STATUS 2026-11-12, "leftover stages"). Built as written,
with two additions: a stage the run summary lists as succeeded is never marked,
whatever the file times say (a disk clock behind the machine clock must not
paint fresh output hollow); and a second reason, `older_than_upstream`, for a
stage older than one before it — the book-box editor's "Save & re-split" runs
Stage 02 alone, which no failed run records. Both carry a 2 s slack.

**Problem.** `pipeline/run_all.py` stops at the first failing stage and leaves
the later stage folders as they were. After a *re-run* that fails at Stage 03,
folders 04–06 still hold the previous run's output, and the console shows them
as fine. Stage 07 now warns about such a page (`page_readiness` → `stale`),
but the page view does not show *which* stages are old.

**Build.**
1. `run_all.run_page`: record `started_at` (UTC ISO string, taken before the
   first stage) in `PageRunResult` and so in `run_all.json`. Additive field,
   default `None`.
2. `server/jobs.py::_stage_status`: add `"stale": True` when `run_all.json`
   has `started_at`, and the stage's `meta.json` modification time is earlier
   than it. Use the file's mtime; do not add a field to `StageMeta`.
3. Console (`server/assets/console/index.html`, `stagePips` and the page
   view): draw a stale stage's pip hollow, with the tooltip "left over from an
   earlier run"; in the page view, show one line above the tabs: "The last run
   stopped at <stage>. Stages after it are from an earlier run."
4. The Android DTO ignores unknown fields; do not change the app.

**Tests:** `server/tests/test_jobs.py` — a page with `run_all.json`
`started_at` newer than `04_layout/meta.json` reports that stage stale and an
earlier stage not; a page with no `started_at` reports nothing stale (old
jobs). `pipeline/tests/test_run_all.py` — `started_at` is written and parses.

**Do not** delete or move the leftover folders. The stage contract says a
stage writes only its own folder; and the leftovers are what lets a person see
what the page looked like before.

**Done when:** tests pass and a page made to fail by hand (rename
`03_dewarp/` input, re-run) shows hollow pips in the console.

## 3. Stage 00 does not know a page was declared single (imported PDFs)

**DONE 2026-11-12** (Stage 00 v0.2.0; RESULTS 2026-11-12, single-page OSD row;
pre-registration `../data/single_page_osd_prereg_20261112.md`). Step 1 found no
upright page turned (0 of 79 single pages; the one sideways-printed table turned
correctly), so only the warning was fixed, as step 2's first branch says. The
population's PDFs are the text-layer row's, not `jobs/pdfimp_*` (only one such
job exists, 2 pages; both are included).

**Two symptoms, one cause.** `pipeline/stage00_ingest.py` orients every frame
with `tools/normalize.py`'s cascade, which was designed for photographed
*spreads*:

- (noise) every imported single page gets the warning "result is PORTRAIT, but
  a book spread should be landscape" — listed in `../OPEN_PROBLEMS.md` P10.
- (possible wrong rotation, **unmeasured**) the cascade accepts a 90°/270°
  orientation call at confidence 2.0 *because a wrong one makes a spread
  portrait, which the landscape check then catches* (`config.yaml`,
  `ingest.min_osd_conf`). On a single portrait page that safety net points the
  wrong way: a wrong 90° call makes the page landscape, which looks right.

**Step 1 — measure before changing anything** (pre-register in
`docs/data/single_page_osd_prereg_<date>.md`). Population: every page of the
imported-PDF jobs under `jobs/pdfimp_*` plus the PDF fixtures named in
`tools/pdf_import_check.py`; all are upright by construction (a PDF renders
upright). Statistic: on how many does the cascade rotate the page at all, and
at what OSD confidence. Control: the same pages rotated by 90° on purpose must
be rotated back. Report the two confidence distributions the way
`ingest.min_osd_conf_180` was derived (wrong calls' maximum, correct calls'
minimum).

**Step 2 — only then build**, and only what the numbers support:

- If no upright single page is ever rotated: fix the warning only. Stage 00
  reads `<page_dir>/page_layout.json` (it is operator/importer **input** at the
  page-dir root, the same file Stage 02 already reads — say so in the stage's
  docstring and in `CLAUDE.md`'s "Declared-page-layout exception") and drops
  the PORTRAIT warning when `layout == "single"`.
- If some are rotated: for `origin == "pdf_import"` pages, skip the 90°/270°
  branch entirely (keep the 180° branch with its own floor, since a scan bound
  upside down is real). Record `orientation_policy` in the stage's `meta.json`.

**Tests:** a declared-single page gets no PORTRAIT warning; a spread still
does; (if step 2b) an imported page is never turned 90°.

**Do not** change `min_osd_conf` or `min_osd_conf_180`. They were measured on
phone captures and are right for those.

## 4. Pair a caption with a picture on the facing page

**DONE 2026-11-12** (STATUS 2026-11-12, "facing page"). Built as written, with
the precedence made explicit: hand before inferred, then the picture's own page
before the facing page, then reading order; a caption leaves its own page only
if it won the picture, and a facing caption is never added to the picture
page's block list (it would be painted out of the picture by the text mask).
The editor also shows the caption from the picture's side and jumps between
the two pages.

**Problem** (`../OPEN_PROBLEMS.md` P10, last bullet). `Block.figure_ref` is a
`BlockRef(page_id, block_id)`, so the schema can already say "this caption
belongs to that picture on the other page". Neither the editor nor the
renderer acts on it: `pipeline/stage08_render.py` only honours a reference
whose `page_id` equals the caption's own page (search for
`b.figure_ref.page_id == page.page_id`), and the editor's picture picker lists
the current page only. Art books and the owner's guide book both print
captions opposite their pictures.

**Build — editor first, renderer second, nothing automatic.**
1. Editor (`pipeline/assets/editor/index.html`): in the caption's "pair with"
   picker, add the pictures of the *other page of the same spread* (same
   `source_spread`, different `subpage`), labelled "facing page · #id". Saving
   sets `pair_source = "user"` as today.
2. Renderer: when a caption's `figure_ref` points to the facing page, print the
   caption directly under that picture on the facing page and do not print it
   again on its own page. Keep the existing same-page path untouched. If the
   target block is missing, deleted or not a picture, fall back to printing the
   caption where it stands (that is today's behaviour for a dangling
   reference — keep it).
3. `figure_grouping` (the automatic pass) stays page-scoped. **Do not** add
   automatic cross-page pairing: its bar is zero wrong pairs and nothing has
   measured a cross-page rule.

**Tests:** `pipeline/tests/test_stage08_render.py` — a cross-page pair renders
the caption once, under the facing picture; a dangling cross-page reference
renders the caption in place. Editor: add to `pipeline/tests/test_editor.py` (search it
and `tools/` for `pair_source` to find how pairing is driven today).

**Check on real data:** on a copy of the owner's job, pair one of the 12
unpaired captions to a facing-page picture by hand and compare the two page
sections before and after (the caption text must appear exactly once in the
render).

## 5. A focus check for picture upgrades (P7) — pre-registration only

**Steps 1–3 BUILT 2026-11-12; waiting on the owner's answers.** Labelling page
`tools/figure_focus_labels.py`, statistic and refusal-to-score-early
`tools/figure_focus_eval.py`, pre-registration
`../data/figure_focus_prereg_20261112.md`, control passed on the owner's book
(24 of 24: self exactly 1.0, blurred σ 2 at most 0.655;
`../data/figure_focus_20261112/control.json`). Nobody has computed the ratio on
the 11 sweep-job pictures. Next: the owner runs
`python -m tools.figure_focus_labels jobs/20261021-104424-6d43b587/` and answers
11 pictures; then `python -m tools.figure_focus_eval score <answers file>` and a
RESULTS row whichever way it goes.

**Problem.** `pipeline/figure_hires.py` replaces a picture cut from the page
with a cut from a close-up when the close-up is larger, covers it and lines up.
Nothing checks that it is *sharper*: of 24 upgrades on the owner's book at
least 4 look worse than the page crop (`../OPEN_PROBLEMS.md` P7).

**This item is the pre-registration, not the fix**, because the 24 pictures
have already been looked at and cannot be used to choose a rule.

1. Collect verdicts first. Add a tool `tools/figure_focus_labels.py` that, for
   a job, writes an HTML page showing each upgraded picture as **two unlabeled
   tiles in random order** (page crop enlarged to the upgrade's size, and the
   upgrade), with three buttons: left sharper / right sharper / cannot tell.
   Save the answers to `docs/data/figure_focus_labels_<date>.json` with the
   random order recorded. The owner answers; nobody else.
   Population: a job that was **not** the one read in P7 — the sweep job
   `jobs/20261021-104424-6d43b587` (11 upgrades) plus whatever the next shoot
   brings. Say in the prereg that 11 is small.
2. Pre-register the statistic before computing it on those pictures:
   the ratio of mean gradient magnitude (Sobel, on the luminance channel, both
   images brought to the page crop's size with area interpolation) upgrade ÷
   crop; gate "upgrade ships only if ratio ≥ 1.0"; pass if it agrees with the
   owner on ≥ 90 % of the pictures the owner could tell apart **and** never
   ships one the owner called worse.
3. Control: a picture blurred on purpose (Gaussian σ = 2) must score below 1.0
   against itself; a picture against itself must score exactly 1.0.

**Do not** tune the ratio's threshold on the labelled pictures, and do not use
the checkerboard view for this — it shows alignment, not sharpness.

## 6. The fraction flag for model-read tables (P2a) — ready to run after the next shoot

**Problem.** A local model reads the owner's tables at 1.6 % word error where
Tesseract manages 71.5 %, but it reads a printed ¾ as ¼, and no second opinion
tested so far catches that. Model text may not reach a PDF until something
flags its mistakes (owner's condition, `CLAUDE.md`).

**The untested cheap rule:** flag *every* token that contains a fraction
character (¼ ½ ¾ and the `n/n` forms) or a digit next to one, so the operator
checks each against the picture. It would have caught all 9 misreadings seen.
Its cost — how many flags per table, and whether there are number misreadings
that are not fractions — is unknown.

**This needs blocks nobody has read yet** (the 28 blocks of the 2026-10-21 test
are spent). So:

1. Wait for the shoot in `closeup-shotlist-tables-panels.md`, or use tables
   from a second book.
2. Before reading them, write `docs/data/fraction_flag_prereg_<date>.md`:
   population (the new table blocks, listed by page and block id), ground truth
   (typed by hand from the photograph *before* the model runs), statistic
   (share of wrong number tokens that carry a flag; share of all tokens
   flagged), gate (every wrong number flagged; at most 25 % of tokens flagged —
   the same bar as the 2026-10-21 row), control (the rule on Tesseract's text of
   a clean body-text block must flag almost nothing).
3. Reuse the reader and scorer in `docs/data/panelread_20261021/`; do not edit
   its prompt (an edited prompt is an unmeasured prompt).
4. Write the RESULTS row whichever way it goes.

**Do not** ship model text into `document.json` as part of this. The outcome of
this item is a number and a decision for the owner.
